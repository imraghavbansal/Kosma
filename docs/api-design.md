# Kosma API Design (V1) - as actually built

This describes the real, implemented API surface, not the original Phase 0 plan -
a couple of endpoints originally sketched (a demo/seed HTTP endpoint,
`/v1/analytics/overview`) were never built because the seed script and
`create_regression_tests`/`ship` flows covered the same need more directly; see
`docs/development-plan.md` for what shipped in which phase. Everything past Phase
9 (self-serve onboarding, GitHub OAuth and the GitHub App PR bot, real per-project
LLM replay, behavioral memory, command center, the scorecard endpoint) was added
after the original Phase 0 plan and is documented here as built. OpenAPI docs are
auto-generated by FastAPI at `/docs` on the running API.

Two auth schemes:
- **Ingestion** (`POST /v1/traces`): `Authorization: Bearer <project_api_key>`, checked
  against `projects.api_key_hash`.
- **Dashboard/query/change-engine endpoints**: a signed session cookie, set either by
  `POST /v1/auth/login` (shared secret) or the GitHub OAuth flow - both produce an
  equally-privileged session (see `docs/architecture.md`'s OAuth scoping note).

List endpoints return `{items: [...], total: int}` (or just a plain object where
there's no natural list, e.g. `/v1/analytics/failure-clusters`). All errors return
`{error: {code, message, request_id}}` with the appropriate HTTP status;
`RequestValidationError` (422) additionally includes `details`.

## Auth

```
POST /v1/auth/login          { secret } -> sets session cookie
POST /v1/auth/logout         -> clears session cookie
GET  /v1/auth/me             -> { authenticated, user: {github_username, display_name,
                                   avatar_url} | null }   (null = shared-secret session)

GET  /v1/auth/github/login    -> 307 redirect to GitHub's OAuth authorize page
                                  (503 if GITHUB_CLIENT_ID isn't configured)
GET  /v1/auth/github/callback -> exchanges the code, upserts the user, sets the
                                  session cookie, redirects to FRONTEND_URL/dashboard
```

## Ingestion

```
POST /v1/traces
  body: { trace_ref, agent_id, agent_config_id, workflow_tag?, segment_tags?,
          input_text, model_provider?, model_name?, status?, success?, latency_ms?,
          input_tokens?, output_tokens?,
          spans: [ { ref, parent_ref?, span_type, name, input?, output?, metadata?,
                     latency_ms?, error?, tool_call?, retrieval_event? } ] }
  -> 202 { trace_id, status: "queued" }
```
Idempotent on `trace_ref`: re-posting the same `trace_ref` (e.g. after a client-side
timeout on a request that actually succeeded) returns the existing trace rather than
erroring or duplicating. The SDK submits one complete trace payload on completion - no
partial/streaming ingestion in V1.

## Traces (evidence / secondary nav)

```
GET /v1/traces?workflow_tag=&limit=&offset=          -> paginated list
GET /v1/traces/{id}     -> trace + full span tree (spans, tool_calls, retrieval_events)
```

## Agents & configs

```
GET  /v1/agents                    -> every agent for the project, each with its configs
POST /v1/agents/{id}/configs
  body: { kind: "prompt"|"model", version_label, prompt_text?, model_provider?,
          model_name?, is_baseline? }
  -> 201 { agent_config }
```

## Projects

```
POST  /v1/projects
  body: { name, github_repo? }
  -> 201 { id, name, github_repo, api_key: "kosma_live_...", agent_id, agent_config_id }
     (self-serve onboarding: also creates the org, a default agent, and its
     baseline agent_config; the API key is shown once and never again)

GET   /v1/projects            -> { items: [{ id, name, github_repo, agent_count,
                                    trace_count, change_proposal_count, created_at,
                                    real_replay_configured, llm_provider }] }
GET   /v1/projects/{id}       -> project detail: agents (with configs), change_proposals,
                                    real_replay_configured, llm_provider

PATCH /v1/projects/{id}
  body: { github_repo?, llm_provider?, llm_api_key? }   (only fields sent are touched)
  -> 200 { project summary }   (llm_provider must be "openai" or "anthropic")

POST  /v1/projects/{id}/regenerate-key
  -> 200 { api_key }   (invalidates the old key; never stored/returned in plaintext again)
```

## GitHub (OAuth-scoped activity)

Real data for the signed-in GitHub-OAuth user, fetched live from the GitHub API using
the access token captured during OAuth - 403 if the session isn't GitHub-authenticated.

```
GET /v1/github/repos                        -> { items: [{ name, description, url, stars,
                                                  language, pushed_at, private }] }
GET /v1/github/activity                     -> recent commits/PRs across the user's most
                                                  recently pushed repos, capped for speed
GET /v1/github/repos/{owner}/{repo}/activity -> commits/PRs for one specific repo
```

## GitHub App webhook (PR bot)

```
POST /v1/github/webhook
  headers: x-hub-signature-256, x-github-event
  -> 200 { status: "commented"|"ignored", ... }
```
On a `pull_request` event (opened/synchronize/reopened) for a repo linked to a Kosma
project (`Project.github_repo`), posts that project's most recent analyzed change's
verdict as a real PR comment. Verifies the webhook signature against
`GITHUB_APP_WEBHOOK_SECRET`; 503 if the GitHub App isn't configured on this deployment.
Does not analyze the diff itself - it surfaces the most recent already-computed verdict,
not a fresh fabrication triggered by the PR's contents.

## Behavioral memory

```
GET /v1/behavioral-memory?q=
  -> { query, total, items: [{ id, description, agent_name, status, created_at,
       recommendation, confidence, worst_segment, outcome_summary }] }
```
Deterministic substring search over every change proposal ever made (description, agent
name, segment labels) - not embeddings, matching this product's "deterministic first"
default (see `docs/architecture.md`).

## Command center

```
GET /v1/command-center
  -> { waiting_for_review, highest_risk, recent_verdicts, awaiting_outcome_verification,
       prediction_accuracy: { calibration_rate, segments_evaluated } }
```
The dashboard home's triage view: proposals waiting on review, the highest-risk ones
(BLOCK/MODIFY), the most recent verdicts, shipped proposals still waiting on enough
live traffic to confirm an outcome, and Kosma's own calibration rate.

## Scorecard

```
GET /v1/scorecard/calibration
  -> compute_calibration_summary(db): Kosma's own prediction accuracy, graded from
     every prediction_outcome computed so far
```

## Public

```
GET /v1/public/stats
  -> { total_traces, total_analyzed_changes, latest_impact_report }
```
Unauthenticated. Real aggregate counts and the latest report's segment deltas only - no
trace content, no input text, no evidence trace IDs. Powers the login page's Blast Radius
Diff visual with real (not illustrative) data.

## Change engine (the core product surface)

```
POST /v1/change-proposals
  body: { agent_id, baseline_config_id, candidate_config_id, description? }
  -> 201 { change_proposal }

GET  /v1/change-proposals            -> { items, total }
GET  /v1/change-proposals/{id}

POST /v1/change-proposals/{id}/analyze
  -> 200 { impact_report }   (idempotent - re-posting an analyzed proposal returns
                               the existing report rather than re-running it)

GET  /v1/change-proposals/{id}/impact-report
  -> 200 { recommendation, confidence, cohort_size, sample_size,
           overall_metrics, segment_metrics, evidence: [...] }
     404 if not yet analyzed

POST /v1/change-proposals/{id}/ship
  -> 200 { change_proposal }   (422 if not yet analyzed; sets status=shipped)

GET  /v1/change-proposals/{id}/prediction-outcome
  -> 200 { predicted_metrics, actual_metrics, prediction_error }  (per segment;
     a segment with too little live candidate-config traffic reports
     {status: "insufficient_data"} rather than a fabricated number)
     404 if not shipped or no impact report exists
```

## Regression tests

```
POST /v1/impact-reports/{impact_report_id}/regression-tests
  -> 201 { items: [...], total }   (generated from evidence rows the analysis
                                     marked "regressed"; idempotent, capped at 10)

GET  /v1/regression-tests            -> { items, total }
GET  /v1/regression-tests/{id}
```

## Analytics

```
GET /v1/analytics/failure-clusters
  -> { clusters: [{ label, workflow, region, count, sample_trace_ids }],
       total_failures }
```
Real failed traces grouped by workflow+region on demand - not the embedding-based
clustering described as a future direction in PRODUCT-SPEC.md, an honest simpler
aggregation over actual data.

## Health

```
GET /health   -> { status: "ok" }   (also confirms DB connectivity)
```
